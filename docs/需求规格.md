# KeyHold 需求规格

状态：已重新对齐，已实施，等待远程 CI 验收
日期：2026-08-07

## 1. 一句话定义

KeyHold 是一种单密码、单私钥的 JSON 备份格式，并提供 TypeScript 与 Go 两种语义一致的 SDK。

一个 KeyHold Document 必须且只能表达：

- 一个必填 label；
- 一把 secp256k1 私钥的公开身份；
- 一个密码派生过程；
- 一份由该密码加密的私钥密文。

不存在 protector 概念，不支持一个文件多个密码，也不支持一个文件多把私钥。

## 2. 设计原则

1. 加密参数完整写入 JSON，不依赖隐藏 profile 或代码约定。
2. 算法名、字段名、数值类型和长度单位均由规范封闭定义，不允许自由拼写。
3. 文件中的每个字段都必须真实参与解析、展示或密码学运算；不用的字段删除。
4. 顶层 `label` 必填，不放进 metadata。
5. `format` 固定为 `keymaster`。
6. 数据库和采用方应靠向 KeyHold Document；KeyHold 不复制产品数据库字段。
7. 保持简单，不为未确定的未来需求预留数组、wrapper 或扩展字段。
8. 格式层没有默认参数；SDK 只提供推荐参数，调用方必须明确选择，最终实际参数必须完整写入 JSON。
9. 加密状态直接组装与明文私钥完整加密是两个 SDK 入口，但必须输出同一种 Document。

## 3. 唯一数据结构

```json
{
  "format": "keymaster",
  "version": 2,
  "label": "Personal key",
  "publicKeyHex": "02...",
  "keyDerivation": {
    "algorithm": "pbkdf2-hmac-sha-256",
    "passwordEncoding": "utf-8",
    "iterations": 600000,
    "outputLengthBits": 256,
    "saltB64Url": "..."
  },
  "cipher": {
    "algorithm": "aes-gcm",
    "keyLengthBits": 256,
    "ivB64Url": "...",
    "tagLengthBits": 128,
    "ciphertextAndTagB64Url": "..."
  }
}
```

顶层只允许：

- `format`
- `version`
- `label`
- `publicKeyHex`
- `keyDerivation`
- `cipher`

所有字段必填。任何其他字段都属于非法输入。

## 4. 公共字段

### 4.1 `format`

- 必须是小写字符串 `keymaster`。
- 不接受 `keyhold`、其他大小写或别名。

### 4.2 `version`

- 必须是 JSON 十进制整数 `2`。
- 不接受字符串、浮点数、指数写法或其他版本。

### 4.3 `label`

- 必须是非空 Unicode 字符串。
- SDK 不 trim、不做 Unicode normalization。
- 不规定最大长度。
- 只用于展示，不参与 KDF 或 AES-GCM。
- 由于本版本不使用 AAD，label 不提供密码学防篡改承诺。

### 4.4 `publicKeyHex`

- 必须是恰好 66 个字符的小写 hex，不带 `0x` 前缀。
- 解码后必须是有效的 33-byte compressed SEC1 secp256k1 public key。
- 首 byte 必须为 `0x02` 或 `0x03`。
- 明文私钥导出时由 SDK 从输入私钥派生，不允许调用方同时提供第二份 public key。
- 解密后，SDK 必须从私钥重新派生 public key，并按 bytes 与本字段比较。

## 5. 编码规则

- JSON 文本使用 UTF-8。
- `publicKeyHex` 使用小写 hex，方便识别并符合 secp256k1 公钥的常见表达。
- salt、IV、ciphertext 和 GCM tag 等不透明 bytes 使用 RFC 4648 URL-safe base64，无 `=` padding。
- base64url 字段名必须以 `B64Url` 结尾；hex 字段名必须以 `Hex` 结尾。
- decoder 拒绝 `+`、`/`、`=`、空白、换行、非法字符和非 canonical pad bits。
- SDK 不猜测编码，不兼容“字段名是 base64、实际内容是 hex”的错误行为。
- JSON object 不允许重复字段名。
- JSON 字符串不得包含未配对 surrogate。
- 所有整数必须写成十进制整数 literal，不接受小数或指数形式。

## 6. 私钥明文

- AES-GCM plaintext 固定为原始 32-byte secp256k1 private key。
- 不是 hex 字符串、WIF、JSON、助记词或其他包装结构。
- 私钥数值必须满足 `1 <= d < secp256k1.n`。
- SDK 解锁成功后只返回 private key bytes 和从其派生的 compressed public key，不生成 address 或 WIF。

## 7. 密码派生

`keyDerivation` 只允许以下字段：

| 字段 | 类型 | v2 规则 |
| --- | --- | --- |
| `algorithm` | string | 固定 `pbkdf2-hmac-sha-256` |
| `passwordEncoding` | string | 固定 `utf-8` |
| `iterations` | integer | `1..2147483647`，必须使用文件原值 |
| `outputLengthBits` | integer | 固定 `256` |
| `saltB64Url` | string | 解码后恰好 16 bytes |

参数规则：

- 密码本身永远不写入 Document。
- 格式没有默认 iterations；缺失即为非法 Document，SDK 不补值。
- SDK 发布的当前推荐 iterations 是 `600000`，它是推荐值，不是隐藏默认值或格式常量下限。
- SDK 必须提供可显式取得的推荐参数对象；调用方把该对象或自己选择的合法参数明确传入明文导出 API。
- 即使调用方选择推荐参数，实际 `algorithm`、`passwordEncoding`、`iterations` 和 `outputLengthBits` 仍必须全部写入 JSON。
- 每次明文私钥导出必须生成新的 16-byte 密码学安全随机 salt。
- 密码必须是非空 Unicode scalar sequence。
- 密码按原始字符序列编码为 UTF-8；不 trim、不变更大小写、不做 Unicode normalization。
- PBKDF2 输出的 32 bytes 直接作为 AES-256-GCM key，不再做第二次 KDF 或隐藏转换。

salt 必须保存在文件中，因为相同密码只有结合创建时的 salt 和 iterations，才能在解密时派生出相同 AES key。salt 不是秘密。

Document 不保存 password verifier。密码是否正确由 AES-GCM 能否成功解密以及解密后 public key 是否匹配共同确定。

## 8. 私钥加密

`cipher` 只允许以下字段：

| 字段 | 类型 | v2 规则 |
| --- | --- | --- |
| `algorithm` | string | 固定 `aes-gcm` |
| `keyLengthBits` | integer | 固定 `256` |
| `ivB64Url` | string | 解码后恰好 12 bytes |
| `tagLengthBits` | integer | 固定 `128` |
| `ciphertextAndTagB64Url` | string | 解码后恰好 48 bytes |

加密规则：

- plaintext 是 32-byte private key。
- 每次加密必须生成新的 12-byte 密码学安全随机 IV。
- AES-GCM 输出按 `ciphertext || tag` 保存到一个字段：前 32 bytes 是 ciphertext，最后 16 bytes 是 GCM tag。
- 合并保存用于减少字段数量；字段名明确说明包含 ciphertext 和 tag，不形成隐藏约定。
- `tagLengthBits` 明确规定末尾 tag 的长度。
- 不使用 AAD；TypeScript 省略 `additionalData`，Go 传 `nil` additional data。
- GCM tag 是 AES-GCM 解密和错误密码判断所必需的固有输出，不是额外 checksum、签名或业务校验文件。
- 不保存 `cipherSalt`。AES-GCM 使用 IV，不使用 salt；文件中的 salt 只属于 PBKDF2。

### 8.1 SDK 推荐参数

SDK 当前推荐以下“明文导出参数”，但不得自动采用：

```json
{
  "keyDerivation": {
    "algorithm": "pbkdf2-hmac-sha-256",
    "passwordEncoding": "utf-8",
    "iterations": 600000,
    "outputLengthBits": 256
  },
  "cipher": {
    "algorithm": "aes-gcm",
    "keyLengthBits": 256,
    "tagLengthBits": 128
  }
}
```

推荐对象不包含随机 salt、IV 或 ciphertext。调用方必须明确把推荐对象传给明文私钥导出；SDK 随后生成随机 salt/IV，并把推荐对象和生成结果一起完整写入 Document。

## 9. 两种导出模式

两种模式生成完全相同的 KeyHold Document。区别只在于 SDK 接收的是已有加密状态，还是明文私钥和密码。

### 9.1 加密状态导出

适用于采用方的持久化记录已经遵循 KeyHold 的全部密码学语义。该模式不需要密码和 private key，不执行 PBKDF2、AES-GCM 解密或重新加密。

SDK 输入必须包含：

- `label`；
- `publicKeyHex`；
- 完整且显式的 KDF 参数；
- 16-byte salt；
- 完整且显式的 cipher 参数；
- 12-byte IV；
- 48-byte `ciphertext || tag`。

二进制输入使用 raw bytes，由 SDK 统一编码为 canonical base64url。SDK 必须：

1. 固定写入 `format=keymaster` 和 `version=2`。
2. 验证所有公开字段、参数关键字、数值和 bytes 长度。
3. 原样使用调用方传入的 salt、IV 和 ciphertext/tag；不生成随机值。
4. 组装并序列化完整 Document。

由于该模式没有密码和 private key，SDK 只能验证结构，无法证明 ciphertext 实际解密为 `publicKeyHex` 对应的 private key。采用方必须保证存储时已经使用以下语义：

- plaintext 是原始 32-byte private key；
- AES key 由该文件中的 PBKDF2 参数和 salt 派生；
- AES-GCM 不使用 AAD；
- ciphertext 末尾包含 16-byte tag。

如果来源密文使用不同 plaintext、AAD、KDF、key、IV 或 tag 布局，即使字段长度能够组装，也不得使用加密状态导出；必须改走明文私钥导出。

### 9.2 明文私钥导出

调用方先在自己的安全边界内取得 private key，再交给 SDK 完整生成 KeyHold Document。

输入：

- 32-byte private key；
- 一个非空密码；
- 一个非空 label；
- 一组显式 KDF/cipher 参数；调用方可以显式传入 SDK 推荐参数对象。

SDK 必须：

1. 验证 private key。
2. 派生 `publicKeyHex`。
3. 生成随机 salt 和 IV。
4. 根据写入文件的 PBKDF2 参数派生 AES key。
5. 使用 AES-256-GCM 加密 private key。
6. 组装并序列化完整 Document；任一步失败都不得返回部分结果。

SDK 不允许省略参数后静默采用推荐值。推荐参数必须由调用方明确取得并传入。

### 9.3 导入

- `parse` 将 UTF-8 JSON 解析并严格验证为 Document。
- 导入只验证结构和公开字段，不索要密码、不尝试解密。
- 导入不迁移、不改写、不猜测其他格式。

### 9.4 解锁

输入一个 Document 和一个密码：

1. 使用 Document 中的 salt、iterations 和其他 KDF 参数派生 AES key。
2. 使用 Document 中的 IV、tag length 和密文执行 AES-GCM 解密。
3. 验证结果是合法 32-byte secp256k1 private key。
4. 派生 compressed public key 并匹配 `publicKeyHex`。
5. 全部成功才返回 private key。

密码错误、ciphertext/tag 损坏、解密结果非法或 public key 不匹配，对外统一返回 `unlock_failed`，不暴露失败发生在哪一步。

### 9.5 已有 Document 序列化与持久化

- `serialize` 只验证并序列化当前 Document。
- 不索要密码，不解密，不重新加密，不刷新 salt 或 IV。
- 采用方可以直接把完整 Document 作为密文存储记录。
- 数据库 ID、active 状态、时间戳等产品字段必须放在 Document 外部。

### 9.6 更换密码

格式不提供多个密码或 password slot。更换密码必须：

1. 用旧密码完整解锁；
2. 用同一 private key、原 label、新密码和显式参数重新执行明文私钥导出；
3. 由调用方原子替换旧 Document。

SDK 不提供“不解密直接添加密码”的能力。

## 10. SDK 公共能力

TypeScript SDK 与 Go SDK 必须提供语义等价的最小能力：

- `recommendedParameters`：返回一份普通、完整、可检查的推荐参数对象，不产生 Document，也不形成默认行为。
- `exportEncryptedState`：从已符合 KeyHold 语义的加密状态组装并返回 JSON，不执行 KDF、加密或解密。
- `exportPrivateKey`：从 private key、密码、label 和显式参数完成加密并返回 JSON。
- `parse`：JSON/UTF-8 bytes 转换为已验证 Document。
- `validate`：验证内存中的未知对象或 Document。
- `serialize`：Document 转换为 JSON。
- `unlock`：使用一个密码解锁 Document。
- `summary`：返回不含密码、private key、完整 ciphertext/tag 的公开摘要。

两种语言可以使用符合各自习惯的函数名，但字段、输入语义、输出语义、错误码和测试向量必须一致。

不提供：

- protector 增删接口；
- 多密码尝试接口；
- WebAuthn/Passkey API；
- address/WIF/metadata API；
- 文件选择、下载、数据库或 UI API；
- 自动选用推荐参数的无参数导出 API。

## 11. 稳定错误码

| 错误码 | 含义 |
| --- | --- |
| `invalid_json` | JSON、UTF-8、重复字段或 Unicode 结构非法 |
| `unsupported_format` | `format` 不是 `keymaster` |
| `unsupported_version` | `version` 不是整数 `2` |
| `invalid_document` | 字段、类型、编码、长度或交叉关系非法 |
| `unsupported_algorithm` | KDF/cipher 关键字不受支持 |
| `invalid_parameter` | 导出 API 的密码、label、参数或 bytes 输入非法 |
| `invalid_private_key` | 明文导出时 private key 长度或 secp256k1 范围非法 |
| `unlock_failed` | 密码错误、密文损坏、tag 错误或解密后身份不匹配 |

错误不得包含密码、派生 AES key、private key、完整 ciphertext 或 tag。

## 12. 特殊情况

- 空密码：明文导出时返回 `invalid_parameter`；解锁时按普通错误密码处理并返回 `unlock_failed`。
- label 为空：两种导出均返回 `invalid_parameter`；导入返回 `invalid_document`。
- 相同私钥和密码重复执行明文导出：合法，但必须因为新 salt/IV 得到不同密文。
- 加密状态导出收到推荐值以外但格式合法的 iterations：保留实际值，不替换为推荐值。
- 加密状态导出的公开字段和 bytes 长度合法但来源语义不兼容：SDK 无法在无密码情况下识别；调用方违反前置条件，生成文件可能只能在解锁时返回 `unlock_failed`。
- 文件公开字段被修改：parse 通过与否取决于字段本身；最终无法匹配私钥身份时返回 `unlock_failed`。
- 忘记密码：没有恢复通道，文件无法解密。KeyHold 不保存 verifier、找回信息或第二密码。
- 修改密码：必须先解密再执行明文私钥导出，不能在密文上直接修改 KDF 参数。
- iterations 很高：解锁必须忠实执行文件参数；当前格式不设置额外资源策略，也不静默降低次数。
- 随机源失败：明文私钥导出立即失败，不使用时间戳、`Math.random` 或其他伪随机回退。
- JSON 字段顺序、缩进和换行不同：语义不变，不要求 byte-for-byte 一致。

## 13. 明确删除的设计

KeyHold v2 不存在以下内容：

- `protectors` 数组及 protector 类型；
- `webauthn-prf`、credential ID、RP ID、transport 或 PRF input；
- 多 Password 顺序尝试；
- Vault verifier、全局密码或 Vault 状态；
- metadata、address、network、WIF、source、capabilities、createdAt；
- `cipherSalt`、隐藏 KDF profile 或未参与运算的参数；
- AAD、JCS、checksum、独立 hash、签名、CEK 或 key-wrap；
- 多私钥 container、历史 reader、migration、dual reader 或 dual writer。

## 14. 一致性验收原则

- TypeScript 与 Go 共用一份 JSON Schema、fixtures 和固定密码学测试向量。
- 对固定 private key、密码、salt、IV 和 iterations，两种语言必须产生相同 public key、派生 key、ciphertext 和 tag。
- 对同一组固定加密材料，两种语言的加密状态导出必须产生语义相同的 Document。
- 固定随机材料下，明文私钥导出和加密状态导出组装出的 Document 必须完全等价。
- 任一 SDK 生成的 Document 必须能被另一个 SDK parse、validate、serialize 和 unlock。
- 相同非法输入必须返回相同稳定错误码。
- 生产创建必须使用密码学安全随机源；固定 salt/IV 只能出现在测试中。
- SDK 不自行实现 PBKDF2、AES-GCM 或 secp256k1 primitive。
